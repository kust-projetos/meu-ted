## Operações e paridade

Paridade é medida por cada operação PWA concreta. O denominador único e canônico é a tabela “Registro canônico de operações PWA” abaixo. Inventários de routes/tools e tabelas anteriores são crosswalks técnicos, não denominadores alternativos. Cada linha tem exatamente 9 campos: operação, frase NL (ou `UI-only/Sem NL` explícito), ação PWA→API, status TED, classe de obrigação, dependências/auth, teste+gap, prioridade/slice e aceite observável. `mandatory`, `internal`, `justified exception` e `outside current product` são as quatro classes de obrigação TED. `absent`, `partial`, `implemented` e `blocked` descrevem status atual, nunca obrigação. Onde a célula usa prosa `no TED`, isso significa `blocked` para boundary/admin/internal deliberado e `absent` para operação `mandatory`; `sem operação conversacional comprovada` significa `absent`. “Justified exception” exige a razão específica na linha; “outside current product” só vale se não há operação/consumidor PWA ou produto a exclui explicitamente. `ISOLATE` sozinho não justifica exceção nem remoção.

#### Corpus mínimo observável

Sete prompts devem existir no corpus de regressão e mapear a operação alvo sem exigir literal idêntico: “gastei 50 com carne”; “quanto gastei este mês”; “crie conta Nubank”; “renomeie Aurora Reserva”; “quais contas pagar”; “corrija valor daquele gasto”; “desfaça última ação”. Para cada caso guardar contexto inicial, operação/slots esperados, chamadas API esperadas/proibidas, número de turnos, necessidade de pergunta/confirm, receipt/efeito e teste de replay. “Desfaça última ação” usa o protocolo undo existente e autoria ADR-028; não é mutation genérica.

#### Métricas de UX: protocolo, não resultados alegados

Medir baseline A e cada candidata no mesmo corpus/contexto/versão, com oráculo independente e estratos simples/difíceis/paráfrase/follow-up/histórico. Reportar numerador, denominador, IC quando aplicável, por domínio e agregado; nunca preencher números sem execução. Métricas: conclusão correta; turnos até conclusão; perguntas redundantes; confirmações redundantes; recusa indevida; inferência de categoria; resolução de entidade; reutilização de contexto; leituras API por tarefa; erros de interpretação simples; falso sucesso sem receipt válido (tolerância zero). Separar confirmação de UX removível (repetição sem ganho) de confirmação/consentimento exigido por risco, e de validação invisível obrigatória (schema, escopo, CAS, idempotência, receipt), que nunca é removida.

**Resultado CAP ↔ HTTP:** 54/54 specs correspondem nominalmente a CAP `api` rows após normalizar aliases já existentes (`budgetTrendsTool`→`budget_trends`, `updateBudgetTool`→`update_budget`, e os nomes camelCase de payables). Nenhum CAP `api` novo e nenhum tool HTTP órfão; `planned` não vira tool. API route registry inclui endpoints de produto que não são OpenAPI tools (crosswalk não afirma cobertura universal de rotas). CAP-075 não é capacidade nova, mas operação real de duplicate check. HTTP `POST detect_duplicate` é semântico de leitura; boundary genérico atual classifica qualquer método não-GET como write — discrepância de policy/UX que deixa a tool gerada bloqueada, embora o consumidor PWA chame a rota.

**Seleção conferida por AST das skills:** `list_categories` e `spending_insights` são CORE. As três ferramentas HTTP `create_category`, `update_category`, `deactivate_category` não aparecem em arrays de tools das skills atuais nem no CORE: além do bloqueio de escrita, não são selecionadas por `selectToolsFor`. As demais ferramentas não aposentadas aparecem no CORE ou em pelo menos uma skill, sujeitas ao teto/ordem; essa elegibilidade não garante exposição em todo turno. `checkToolExecutionPolicy` atualmente recusa toda escrita, mesmo recebendo `_attestation`: não existe ali bypass comprovado por passar atestação opaca. O fluxo V2 é separado.

**Rotas não equivalem a tools:** normalizando parâmetros de path, 51 das 54 HTTP tools correspondem às entradas do inventário de 120 rotas; as três exceções são details/approve/reject V1 retiradas do modelo e sem handler literal encontrado. O handler `pending-operations.ts` registra também 15 paths V2, incluindo aliases, que não estão nas 120 entradas. A [auditoria](TED-CAPABILITY-AND-ARCHITECTURE-AUDIT.md#superfície-v2-complementar-ao-inventário-de-rotas) contém método/capability/schema/resultado de todos esses registros. Não usar o inventário de 120 como lista exaustiva de handlers ou como número de jornadas.

### API rotas existentes fora de ROUTE_INVENTORY

O route registry declara 120 IDs, mas não exaure todo handler montado. Exemplo confirmado: `apps/api/src/routes/index.ts` monta `registerPriceAlertRoutes` apenas se `deps.enablePriceAlerts ?? isPriceAlertsEnabled()`; `PI_FEATURE_PRICE_ALERTS` default OFF e composição de produção passa nada. `price-alerts.ts` expõe GET/POST `/alerts/price` e POST `/alerts/price/check`, autenticando via resolver de device/context, mas store é in-memory e check usa preço mock determinístico. ### Registro canônico de operações PWA (denominador de paridade)

Esta é a única tabela normativa de paridade. Uma linha representa uma ação/read independente utilizável na PWA; caminhos administrativos ou sem consumidor PWA são classificados explicitamente, não somados a features TED obrigatórias. `mandatory` significa que TED deve alcançar a operação dentro do escopo acordado; `internal` é serviço/ação interna, não UX de membro; `justified exception` requer justificativa de UX/segurança nesta linha; `outside current product` significa que não há operação/consumidor PWA atual (não é desculpa para funcionalidade PWA ausente). Status atuais são estáticos e não equivalem à homologação. Para todos os writes financeiros, identidade/workspace/actor são resolvidos server-side, writer API é autoridade, idempotência keyed e receipt válido são obrigatórios; TED envia só decisão/requestId. Isso não reduz a obrigação de paridade.
