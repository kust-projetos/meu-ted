# Matriz de paridade funcional: PWA, API autoritativa e TED

**Baseline auditada:** checkout local `313f999` (`fix/opennext-preview-props`), inspeção estática; sem chamadas a produção.
**Propósito:** inventário de operações concretas para decidir o que manter, simplificar, substituir, isolar ou remover, sem presumir que toda capacidade deve virar conversa TED.

## Método e convenções

Foram cruzados: `apps/api/src/routes/route-inventory.ts` (auth/ownership/path), `apps/api/openapi/agent-tools.openapi.json` e `apps/agent/src/generated/http-tools.ts` (surface conversacional gerada), páginas/hooks PWA em `apps/pwa/src/features/`, rotas específicas do Agent, testes unitários/integração e os E2E listados abaixo. Cada código HTTP listado é relativo ao prefixo API; no navegador a PWA usa proxy same-origin `/api/backend/*`, TED usa `/api/agent/*` para Worker/DO. Schemas detalhados pertencem aos OpenAPI/schema do handler; não se presume equivalência semântica só por compartilhar tabela ou entidade.

**Contagens reconciliadas por parsing dos artefatos (não grep textual):** `ROUTE_INVENTORY` tem 120 entradas; `ROUTE_COVERAGE_IDS` tem 120 IDs. A literal `const specs = [...] as const` em `apps/agent/src/generated/http-tools.ts` tem **54 specs**; OpenAPI `paths` com `x-pi-tool` tem **54 tools**. Comparação por chave `(name, method, path)` resulta: duplicatas `[]`, generatedOnly `[]`, openApiOnly `[]`. O número preliminar 62, obtido contando ocorrências textuais de `"name"` no TS inteiro, era falso: incluiu nomes de parâmetros/propriedades fora do array `specs`; não há oito tools adicionais/fantasmas a procurar. Snapshot CAP: 75 IDs únicos CAP-001..075, 54 `api` + 21 `planned`. Contagem recalculada das 75 linhas por coluna Coverage: `covered=39`, `api-only=10`, `partial=7`, `chat-only=8`, `internal=11` (soma 75); summary legado registra `35/4/8/14/11`, soma 72. Logo há **três linhas de diferença no resumo**, não três IDs ausentes: os IDs são únicos e linhas CAP contadas são 75; buckets do resumo estão stale/incorretos em mais de uma categoria. Não há evidência para atribuir especificamente quais três linhas foram “omitidas”; documentar como erro de agregação, não inventar IDs. Universos separados: rotas, HTTP tools, CAPs planned e fluxos UI.

**Evidência:** `E2E existente` significa arquivo de teste encontrado, não executado nesta auditoria. `Histórica` é relato datado e não comprova funcionamento atual. `Não demonstrada` indica ausência de prova completa, não falha. Auth/persistência/resposta são resumidas por domínio: contexto workspace e membership são resolvidos server-side; mutações seguem idempotência conforme contrato API. A PWA envia decisão/requestId, nunca atestação; Agent executa com capability delegada e receipt validado. Validação independente posterior executou testes unitários e gates, com limites descritos ao final; nenhum E2E atual foi executado.

Legenda de destino: **KEEP** conservar capacidade/caminho; **SIMPLIFY** consolidar UX/fluxo sem perder contrato; **REPLACE** substituição explícita do caminho legado; **ISOLATE** manter em superfície/admin/processamento separado; **REMOVE** candidato a remoção apenas após confirmação de ausência de consumidor/dados. Destino é recomendação auditável, não autorização para alteração.

## Reconciliação nominal dos 54 HTTP tools

Crosswalk abaixo veio de parse dos objetos da literal `specs` e das 54 operações `paths/*/*` com `x-pi-tool` no OpenAPI. `CAP` é a linha cujo tool ID equivale (snake_case/camelCase normalizado); ausência é explicitada. `Selection` descreve a superfície ao modelo: `CORE` = `CORE_READ_TOOLS`; `skill` = incluída somente se skill relevante for selecionada e respeitar teto total 20; `retired` = removida da seleção e também bloqueada em `buildExposedTools`; `write-blocked` = spec gerada, mas a chamada write é recusada por `checkToolExecutionPolicy`, sem atestação opaque V2. Os GET também não são automaticamente todos expostos: skills selecionam subconjunto. CAP-075 não é capacidade nova, mas operação real de duplicate check. HTTP `POST detect_duplicate` é semântico de leitura; boundary genérico atual classifica qualquer método não-GET como write — discrepância de policy/UX que deixa a tool gerada bloqueada, embora o consumidor PWA chame a rota.

As três ferramentas HTTP `create_category`, `update_category`, `deactivate_category` não aparecem em arrays de tools das skills atuais nem no CORE: além do bloqueio de escrita, não são selecionadas por `selectToolsFor`. As demais ferramentas não aposentadas aparecem no CORE ou em pelo menos uma skill, sujeitas ao teto/ordem; essa elegibilidade não garante exposição em todo turno. `checkToolExecutionPolicy` atualmente recusa toda escrita, mesmo recebendo `_attestation`: não existe ali bypass comprovado por passar atestação opaca. O fluxo V2 é separado.

**Rotas não equivalem a tools:** normalizando parâmetros de path, 51 das 54 HTTP tools correspondem às entradas do inventário de 120 rotas; as três exceções são details/approve/reject V1 retiradas do modelo e sem handler literal encontrado. O handler `pending-operations.ts` registra também 15 paths V2, incluindo aliases, que não estão nas 120 entradas. A [auditoria](TED-CAPABILITY-AND-ARCHITECTURE-AUDIT.md#superfície-v2-complementar-ao-inventário-de-rotas) contém método/capability/schema/resultado de todos esses registros. Não usar o inventário de 120 como lista exaustiva de handlers ou como número de jornadas.

### API rotas existentes fora de ROUTE_INVENTORY

O route registry declara 120 IDs, mas não exaure todo handler montado. Exemplo confirmado: `apps/api/src/routes/index.ts` monta `registerPriceAlertRoutes` apenas se `deps.enablePriceAlerts ?? isPriceAlertsEnabled()`; `PI_FEATURE_PRICE_ALERTS` default OFF e composição de produção passa nada. `price-alerts.ts` expõe GET/POST `/alerts/price` e POST `/alerts/price/check`, autenticando via resolver de device/context, mas store é in-memory e check usa preço mock determinístico. Estes são handlers reais condicionais, fora `ROUTE_INVENTORY`, não OpenAPI tool nem capacidade production-backed. Testes: `apps/api/tests/routes/price-alerts.test.ts`, `price-alerts-gating.test.ts`, unit `price-alerts.test.ts`. Portanto: route-inventory omission ≠ rota inexistente; rota montada conditional ≠ feature persistente ativa.

### Canal runtime real: PWA REST, não AIChatAgent SDK

## Fora de escopo, riscos e confiança

- Fora de escopo: redesign, criação de endpoint/tool, decisão de produto, execução de migrations/SQL, dados reais, produção, deploy e quaisquer operações externas.
- Risco alto: leitura superficial de tool catalogue pode sugerir mutações não permitidas em V2; endpoint presente não prova UI acessível ou workflow; agregados PWA podem ser locais; regras de owner/admin e contexto de workspace são invariantes críticas.
- Risco de stale docs: Product (last verified 10/07), Roadmap (10/14) e CAP snapshot (10/04) são anteriores à baseline. ADR-029 é accepted, mas sua validação é declarada “em andamento”; não converter em prova de conclusão.
- Confiança alta: paths/auth/ownership do route registry; presença de páginas e specs pelo filesystem; boundary TED conforme instruções locais/ADR-029. Média: mapeamento UX→endpoint derivado de páginas/hooks e inventário existente. Baixa/não demonstrada: export financeiro, operação conversacional não V2, execução live atual e capacidades planned sem path.
